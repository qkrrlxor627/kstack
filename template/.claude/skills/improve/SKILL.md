# /improve — 평가 기준 → 개선안 문서

인자: `$ARGUMENTS`
- 첫 단어: 버전. 없으면 오늘 날짜(YYYY-MM-DD)를 쓴다.
- 두 번째 이후: 집중할 C/K ID.

## 입력 (읽기 전용)
- 설정: `.claude/kstack.json` — 경로, 발표 시간, 측정 명령
- ID 체계: `criteria.ids` (기본 `doc/criteria/ids.md`). **없으면 멈추고 `/kstack-setup`을 먼저 안내한다.**
- 원문: `criteria.mission`, `criteria.standard` — 판정 근거를 확인할 때 해당 부분을 다시 읽는다
- Before 수치: `bench.results` 폴더(있으면). 수치는 여기 실제 파일에서만 인용한다

## 절차
1. ids.md를 읽고 ID별 체크리스트를 만든다(ID / 기준 / 충족 판단 방법). 사람 확인이 "미확인"이면 그 사실을 문서 첫머리에 적는다.
2. 코드와 참고 문서를 조사해 ID별 현황을 판정한다.
   - 판정은 충족 / 부분 / 미충족 / 미확인 중 하나이고, 근거 파일 경로(가능하면 `파일:줄`과 함수명)를 붙인다.
   - "없다"고 판정하기 전에 실제로 grep으로 다시 찾는다. 기억이나 README 설명만으로 판정하지 않는다.
3. 부분·미충족 항목마다 개선안 P1, P2 …를 쓴다.
   - 순서: 문제 → 근거 K ID → 변경 내용(파일/함수) → 기대 효과 → 측정 방법 → 우선순위(영향×난이도)
   - 발표 시간(`presentation.minutes`)과 마감 안에 할 수 있는지를 우선순위에 반영한다.
   - 수준을 붙인다(L1/L2/L3, 정의는 kstack `METHOD.md`).
4. 같은 폴더의 `template.md` 양식으로 `outputs/improvement-<버전>.md`를 작성한다. 집중 ID가 있으면 그 항목을 깊게 쓴다.
5. `rubric-reviewer` 서브에이전트로 채점받고, FAIL 항목을 고쳐 최종본을 저장한다. 채점 표를 문서 끝 "검토 결과"에 붙인다.
6. 끝에 "사람이 결정해야 할 질문" 목록을 출력한다.

## 규칙
- 산출물은 `outputs/`에만 쓴다. 다른 파일은 수정하지 않는다.
- 모든 개선안은 C ID와 K ID에 매핑한다. 매핑되지 않는 것은 "기준 외 제안"으로 분리한다.
- 미션과 기준표가 충돌하면 임의로 정하지 말고 질문한다(ids.md의 "충돌·공백" 참고).
- 근거 없는 수치나 사실을 만들지 않는다. 수치에는 출처 파일 경로를 붙인다. 확인 못 한 판단은 "(추정)"을 붙인다.
- 커밋은 하지 않는다.
